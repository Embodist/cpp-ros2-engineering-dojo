## 45 jthread 与 stop_token

- 目标：固定周期可取消执行器，停止延迟可测，析构无线程残留。
- 核心概念：`jthread` 析构自动 `request_stop` 再 `join`；`stop_token` 是协作取消，不能强杀；`condition_variable_any::wait_until(lock, token, deadline)` 可按截止时间睡眠且被停止唤醒。
- 参考实现思路：线程循环先等到 `next_deadline` 或 stop，检查 token 后执行任务；`next += period` 固定节拍，落后不补跑；异常在循环内捕获计数；析构显式 `request_stop` 后 `join`，记录停止耗时。
- 关键代码片段 / 实验步骤：

```cpp
class Periodic {
  std::mutex m_; std::condition_variable_any cv_;
  std::chrono::milliseconds period_{100};
  std::atomic<long> errors_{0};
  std::jthread t_;
public:
  explicit Periodic(std::function<void()> job)
    : t_([this, job = std::move(job)](std::stop_token st) {
        auto next = std::chrono::steady_clock::now();
        while (!st.stop_requested()) {
          std::unique_lock lk(m_);
          if (cv_.wait_until(lk, st, next, [&]{ return st.stop_requested(); }))
            break;                         // true 表示收到停止请求
          lk.unlock();
          try { job(); } catch (...) { ++errors_; }
          next += period_;
          auto now = std::chrono::steady_clock::now();
          if (next < now) next = now;      // 落后不补跑
        }
      }) {}
  ~Periodic() { t_.request_stop(); cv_.notify_all(); t_.join(); }
};
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic stage1/labs/45/main.cpp -o stage1/labs/45/run
timeout 10 ./stage1/labs/45/run            # 打印 10 次 stop_latency_us
```

- 验收证据：`max(stop_latency_us)` 应远小于 100ms 周期，而不是接近整周期。反例一改成不可中断的 `sleep_for(period)`，延迟接近一个周期且析构阻塞；反例二改成**无截止时间**的 `cv_.wait(lock, pred)` 且不 `notify_all()`，`join` 挂死，`timeout 10` 退出码 124（`wait_until` 会到截止时间自己醒，不会挂死）。循环创建/析构 1000 次后 `/proc/self/status` 的 `Threads:` 回到基线；ASan 与 TSan 分别构建运行，原始输出贴入 `evidence.md`。
- 常见坑：把 token 当强制终止；锁内执行用户任务；只 `join` 不 `request_stop`；周期漂移与补跑策略未定义。
- 与 ROS2 的关联：回调阻塞会占住 executor 线程，停止延迟变成 executor 关闭时间；按值捕获消息还多一次复制。

## 46 双锁转账死锁

- 目标：复现反向加锁死锁，用 `scoped_lock` 修复，压力下总额不变。
- 核心概念：循环等待；固定锁序或同时加锁；`scoped_lock` 可变参数版用 `try_lock` 轮转；自转账会重复锁同一非递归互斥量。
- 参考实现思路：`Account{cents, mutex}`；错误版先锁 a、`yield` 放大窗口、再锁 b，两线程反向转账；正确版先判同账户返回，再 `scoped_lock(a.m,b.m)` 锁内扣加；8 线程各 100000 次后校验总额与非负。
- 关键代码片段 / 实验步骤：

```cpp
struct Account { int id; long long cents; std::mutex m; };

void transfer_bad(Account& a, Account& b, long long x) {
  std::lock_guard l1(a.m);
  std::this_thread::yield();            // 放大交叉加锁窗口
  std::lock_guard l2(b.m);              // 另一线程反向加锁 -> 死锁
  a.cents -= x; b.cents += x;
}

void transfer_good(Account& a, Account& b, long long x) {
  if (&a == &b) return;                 // 自转账反例
  std::scoped_lock lk(a.m, b.m);        // 同时加锁，避免锁序
  a.cents -= x; b.cents += x;
}
```

```bash
g++ -std=c++20 -O2 -g -pthread stage1/labs/46/main.cpp -o stage1/labs/46/run
timeout 10 ./stage1/labs/46/run bad            # 预期 exit 124
timeout 20 ./stage1/labs/46/run good 8 100000  # 预期 total 不变
```

- 验收证据：正确版打印 `total=<初值> expected=<初值> transfers=800000`；死锁版 `timeout 10` 退出 124，`gdb -p` 后 `thread apply all bt` 看到两线程各持一锁。反例一自转账未判等，重复锁同一互斥量；反例二改用单一全局锁，总额虽不变但掩盖锁序缺陷且吞吐下降；反例三把写回放到锁外，压力下总额漂移。
- 常见坑：只在错误版固定 a→b 顺序，永远复现不了；用地址排序当锁序，不可移植；不变量校验放在锁外；忽略溢出。
- 与 ROS2 的关联：多线程 executor 下两个回调操作共享状态最易反向锁序；回调里再同步等待会放大问题。

## 47 condition_variable 谓词

- 目标：复现丢失唤醒与无谓词等待，改用条件谓词。
- 核心概念：`wait` 原子释放锁并睡眠；`notify` 没有记忆；共享状态必须在同一互斥量下修改；`wait(lock, pred)` 循环复检，可吸收虚假唤醒；`notify_one/all` 与等待者数量相关。
- 参考实现思路：反例生产者先 `push` 并 `notify_one`，再让消费者启动并做无谓词 `wait`，必然睡死；修复版谓词为“队列非空或 stop”，锁内取数据；关闭置 stop 后 `notify_all`；另做无关通知实验，证明必须复检谓词。
- 关键代码片段 / 实验步骤：

```cpp
std::mutex m; std::condition_variable cv;
std::queue<int> q; bool stop = false;

void producer_bad() { { std::lock_guard lk(m); q.push(1); } cv.notify_one(); }
void consumer_bad() { std::unique_lock lk(m); cv.wait(lk); /* 丢失唤醒 */ }

void consumer_ok() {
  std::unique_lock lk(m);
  cv.wait(lk, [&]{ return !q.empty() || stop; });
  if (q.empty()) return;                // stop 被唤醒
  int v = q.front(); q.pop();           // 锁内取走
  cv.notify_one();                      // 唤醒下一个等待者
}
```

```bash
g++ -std=c++20 -O1 -g -pthread stage1/labs/47/main.cpp -o stage1/labs/47/run
timeout 3 ./stage1/labs/47/run bad       # 预期 exit 124
timeout 10 ./stage1/labs/47/run ok 1000  # 预期 consumed=1000
```

- 验收证据：bad 模式 3 秒无消费记录且退出 124；ok 模式 1000 轮均 `consumed=1000` 且无超时。反例一谓词读未加锁的普通 `bool`，TSan 报竞争；反例二关闭只置位不 `notify_all`，消费者仍挂死；反例三一次入两条却只 `notify_one`，第二个等待者可能滞留。原始输出与 TSan 报告写入 `evidence.md`。
- 常见坑：省略谓词；锁外改共享状态；认为 notify 有记忆；持锁做耗时任务；析构前不唤醒等待者。
- 与 ROS2 的关联：单线程 executor 中回调 A 等回调 B 的数据必死锁；应改为事件驱动或队列交接，而非回调内阻塞。

## 48 原子状态机

- 目标：CAS 实现单次初始化，1000 并发恰好一次成功，并说明内存序。
- 核心概念：CAS 是原子的比较后写；`compare_exchange_weak` 会伪失败，需循环刷新 `expected`；release 发布数据、acquire 观察；`relaxed` 只保证原子性，不能发布 payload；状态取 idle/initializing/ready。
- 参考实现思路：`CAS(0→1, acq_rel)` 的赢家写 payload、计数，再 `store(2, release)`；输家 acquire 自旋等 2；异常时复位 0 防永久卡死；另写“先 load 再 store”的错误版对照。
- 关键代码片段 / 实验步骤：

```cpp
std::atomic<int> state{0};                 // 0 idle, 1 initializing, 2 ready
std::atomic<int> init_count{0};
int payload = 0;

bool ensure_init() {
  int expected = 0;
  if (state.compare_exchange_strong(expected, 1,
        std::memory_order_acq_rel)) {
    try { payload = 42; ++init_count; }
    catch (...) { state.store(0, std::memory_order_release); throw; }
    state.store(2, std::memory_order_release);   // 发布 payload
    return true;
  }
  while (state.load(std::memory_order_acquire) != 2)
    std::this_thread::yield();
  return false;
}
```

```bash
g++ -std=c++20 -O2 -g -pthread stage1/labs/48/main.cpp -o stage1/labs/48/run
timeout 10 ./stage1/labs/48/run 1000      # 预期 init_count=1
```

- 验收证据：输出 `callers=1000 init_count=1 ready=1000 payload=42`。反例一用 `load` 后 `store` 的 check-then-act，重复运行出现 `init_count>1`；反例二用 relaxed 发布 payload，TSan/压力循环暴露竞争或未初始化读；反例三异常不复位，后续调用永远自旋，`timeout` 得 124。保存错误版计数与 TSan 输出。
- 常见坑：忽略 weak 伪失败、不刷新 `expected`；relaxed 冒充同步；忙等不退让；两个原子变量表达一个状态。
- 与 ROS2 的关联：多回调并发触发惰性初始化时，必须保证看到 ready 后对象完整；在回调里自旋等 ready 会占住 executor 线程。

## 49 False Sharing 性能测试

- 目标：对比同缓存行与分离行的原子计数器，记录环境与结果变化。
- 核心概念：一致性以 cache line（常见 64B）为单位；两线程写同行的不同变量会互相使行失效；`alignas(64)` 可分离热点；结论依赖 CPU 拓扑、绑核与优化级别。
- 参考实现思路：定义 `Packed` 与 `Padded` 两布局，两线程各对自身计数器做 N 次 `fetch_add(relaxed)`，计时算 ns/op；`taskset` 绑两个物理核，`-O2` 预热一次、正式 5 次，记录 min/p50；打印总和防止被优化删除。
- 关键代码片段 / 实验步骤：

```cpp
struct Packed { std::atomic<long> a{0}, b{0}; };
struct Padded { alignas(64) std::atomic<long> a{0};
                alignas(64) std::atomic<long> b{0}; };

template<class S> double bench(S& s, long n) {
  auto t0 = std::chrono::steady_clock::now();
  std::jthread t([&]{ for (long i = 0; i < n; ++i)
                        s.a.fetch_add(1, std::memory_order_relaxed); });
  for (long i = 0; i < n; ++i)
    s.b.fetch_add(1, std::memory_order_relaxed);
  t.join();
  auto ns = std::chrono::duration<double, std::nano>(
              std::chrono::steady_clock::now() - t0).count();
  return ns / n;
}
```

```bash
g++ -std=c++20 -O2 -pthread stage1/labs/49/main.cpp -o stage1/labs/49/run
taskset -c 2,3 ./stage1/labs/49/run 100000000
```

- 验收证据：输出两布局 ns/op 与 5 次 p50，附 `lscpu`、cache line 大小、编译器、优化级别和绑核命令；只记本机数字，不写固定倍数。反例一单线程时差异消失；反例二不绑核或 `-O0`，被调度与循环开销淹没；反例三改用 seq_cst 后两者都变慢，说明结论只对当前内存序成立。
- 常见坑：计时区含打印；结果未使用被优化删除；用 sanitizer 构建测性能；假设 64B 通用；只跑一次。
- 与 ROS2 的关联：各回调线程更新相邻统计量会出现同类争用；可填充或分片，并记录线程数与速率。

## 50 有界队列背压策略

- 目标：实现丢最新/丢最旧/阻塞三种策略，准确统计丢弃与等待数量。
- 核心概念：满状态是策略输入；阻塞等待“未满或关闭”谓词；队列、计数、关闭标志由同一互斥量保护；消费者取走元素后唤醒生产者；关闭必须唤醒全部等待者。
- 参考实现思路：`push` 锁内判满，分别计数返回、弹队首再入队、或谓词等待；成功入队 `notify_one`；`pop` 取走后 `notify`，计数锁内递增；用单线程确定性用例验证保留内容，双线程压测验证 `produced == consumed + dropped`。
- 关键代码片段 / 实验步骤：

```cpp
enum class Policy { DropNewest, DropOldest, Block };

bool push(int v) {
  std::unique_lock lk(m_);
  if (q_.size() == cap_) {
    if (policy_ == Policy::DropNewest) { ++dropped_; return false; }
    if (policy_ == Policy::DropOldest) { q_.pop_front(); ++dropped_; }
    else {
      ++waiting_;
      not_full_.wait(lk, [&]{ return q_.size() < cap_ || stop_; });
      if (stop_) return false;
    }
  }
  q_.push_back(v);
  not_empty_.notify_one();
  return true;
}
// pop(): 取走后 not_full_.notify_one(); close(): stop_=true; notify_all.
```

```bash
g++ -std=c++20 -O2 -g -pthread stage1/labs/50/main.cpp -o stage1/labs/50/run
timeout 10 ./stage1/labs/50/run drop_newest   # cap=4 连续 push 10
timeout 10 ./stage1/labs/50/run drop_oldest
timeout 10 ./stage1/labs/50/run block
```

- 验收证据：cap=4、push 0..9：DropNewest 保留 `{0,1,2,3}`、`dropped=6`；DropOldest 保留 `{6,7,8,9}`、`dropped=6`；Block 全消费时 `dropped=0` 且 `waiting>0`。压测打印 `produced=100000 consumed=... dropped=...`，守恒式成立。反例一 `pop` 不 notify，生产者仍阻塞（124）；反例二 close 不 `notify_all` 无法退出；反例三锁外计数导致守恒式不成立。
- 常见坑：把丢最旧做成丢新到；等待无谓词；持锁做耗时处理；忽略关闭状态；计数溢出。
- 与 ROS2 的关联：QoS history/depth 是中间件队列深度，不等于应用消费能力；应用层要显式选择丢弃策略并统计。

## 51 Future 超时与取消

- 目标：批量任务用 `wait_for` 超时，超时后对象安全回收，取消语义明确。
- 核心概念：`wait_for` 只观察不取消；future 与共享状态生命周期绑定；`std::async` 的 future 析构可能阻塞等任务；取消需任务协作（token/轮询）；worker 要活到 join，结果写共享状态。
- 参考实现思路：每个任务建 `packaged_task` 并取 future，交线程执行；主线程按统一截止时间 `wait_for`，统计 ready/timeout；超时 future 保持有效，析构时 `request_stop` 后 `join`，验证总耗时覆盖最长任务；文档写清超时后任务是继续、丢弃还是协作取消。
- 关键代码片段 / 实验步骤：

```cpp
std::packaged_task<int()> task([]{
  std::this_thread::sleep_for(std::chrono::milliseconds(500));
  return 7;
});
std::future<int> fut = task.get_future();
std::jthread worker([&](std::stop_token){ task(); });

if (fut.wait_for(std::chrono::milliseconds(100)) ==
    std::future_status::timeout)
  ++timeouts;                       // 超时：任务仍在跑，未被取消
// 作用域结束：worker 析构 request_stop + join
```

```bash
g++ -std=c++20 -O2 -g -pthread stage1/labs/51/main.cpp -o stage1/labs/51/run
timeout 15 ./stage1/labs/51/run            # 打印 ready/timeout 与总耗时
```

- 验收证据：7 个 10ms 任务加 1 个 500ms 任务、截止 100ms，输出 `ready=7 timeout=1`；析构 `shutdown_ms >= 400`，证明超时任务仍被回收。反例一按引用捕获局部结果，ASan 报 stack-use-after-scope；反例二对同一 future `get()` 两次，抛 `future_error`；反例三把超时当取消，日志时间戳显示任务仍跑完。
- 常见坑：`deferred` 分支未处理；忘记 join 触发 terminate；销毁共享状态仍让任务写引用；用 future 做多消费者。
- 与 ROS2 的关联：异步调用 future 在回调里长等会占住线程；丢弃超时 future 不等于取消远端工作，取消需对应机制。

## 52 回调重入陷阱

- 目标：回调内注销自身并再次发布不死锁；递归限深，异常有策略。
- 核心概念：持锁调用用户回调会把注销/再发布变成自死锁；应在锁内拷贝订阅者快照、锁外调用；快照条目调用前复检存活；递归发布需深度上限；异常不能穿出发布边界。
- 参考实现思路：注册表持互斥量、订阅者 vector、id、depth；`publish` 锁内限深并复制快照，解锁后逐个复检、`try/catch`；RAII 守卫减深度；`unsubscribe` 锁内 erase；测试回调 A 首调时注销自己并发布事件 2，回调 B 记录。
- 关键代码片段 / 实验步骤：

```cpp
int publish(Event e) {
  std::vector<std::pair<int, Callback>> snap;
  {
    std::lock_guard lk(m_);
    if (++depth_ > kMaxDepth) { --depth_; ++rejected_; return -1; }
    snap = subs_;                       // 快照
  }
  DepthGuard guard{*this};              // 析构时 --depth_
  int called = 0;
  for (auto& [id, cb] : snap) {         // 锁外调用
    { std::lock_guard lk(m_); if (!alive(id)) continue; }
    try { cb(e); ++called; } catch (...) { ++errors_; }
  }
  return called;
}
```

```bash
g++ -std=c++20 -O2 -g -pthread stage1/labs/52/main.cpp -o stage1/labs/52/run
timeout 5 ./stage1/labs/52/run             # A_calls=1 B_calls=2
timeout 5 ./stage1/labs/52/run recurse     # depth=32 处拒绝
```

- 验收证据：正常输出 `A_calls=1 B_calls=2 errors=0`；递归在 depth=32 被拒绝，不栈溢出。反例一锁内调回调，A 注销自锁，`timeout 5` 得 124；反例二边遍历边 erase，`_GLIBCXX_DEBUG` 或逻辑断言抓到失效，ASan 不保证报告（vector 缓冲区通常未释放）；反例三去掉限深，递归 SIGSEGV；反例四异常逃出，B 收不到后续事件。
- 常见坑：`recursive_mutex` 掩盖设计问题；快照不查存活；持锁抛异常；注销 token 生命周期不一致。
- 与 ROS2 的关联：executor 通常入队而非同步递归，但自定义注册表或进程内通信仍可重入；需说明重入层与限深者。

## 57 时间戳乱序处理

- 目标：实现按 event time 排序的延迟窗口，处理晚到、重复、时间倒退，区分 event/processing time。
- 核心概念：event time 来自数据，processing time 是本地收到时刻；乱序需窗口/水位；超出允许迟到只能丢弃或旁路；重复按来源+序号识别；时间倒退按来源判断，不污染全局水位；策略必须文档化。
- 参考实现思路：记录 src/seq/event，入口用 `steady_clock` 记 arrival；每来源维护 `last_seq/last_event`，按“重复 → 每来源倒退 → 全局过晚”的优先级判断；`max_event` 推水位，`event+lateness<max` 判过晚；其余入小顶堆，`堆顶+window<=max` 时按序发出；结束 flush，统计 dup/late/regress。
- 关键代码片段 / 实验步骤：

```cpp
struct Msg { std::uint64_t src, seq, event_ns; };
void on_msg(Msg m, std::uint64_t arrival_ns) {
  auto& last_seq = last_seq_[m.src];
  if (m.seq <= last_seq) { ++dup_; return; }          // 1) 重复
  if (m.event_ns < last_evt_[m.src]) { ++regress_; return; } // 2) 每来源倒退
  last_seq = m.seq; last_evt_[m.src] = m.event_ns;
  max_event_ = std::max(max_event_, m.event_ns);
  if (m.event_ns + lateness_ < max_event_) { ++late_; return; } // 3) 全局过晚
  heap_.push(m);
  while (!heap_.empty() && heap_.top().event_ns + window_ <= max_event_) {
    emit(heap_.top()); heap_.pop();                    // 按 event 顺序
  }
  (void)arrival_ns;                                    // 另统计 processing 延迟
}
```

```bash
g++ -std=c++20 -O2 -g stage1/labs/57/main.cpp -o stage1/labs/57/run
timeout 5 ./stage1/labs/57/run    # window=2, lateness=5 的确定性输入
```

- 验收证据：输入 s1: `100,102,101,重复100,103`；s2: `90,200,197`。flush 后输出 `100,101,102,103,200`，`dup=1 late=1 regress=1`（90 对 s2 不是倒退，但低于全局水位；197 对 s2 倒退，按优先级计为 regress，不计 late）。反例一不查重，100 发两次；反例二 window=0，101 到达即被放出，顺序变成 `100,102,101`；反例三只按 processing time 排序，网络抖动改变顺序。重复 3 次结果一致。
- 常见坑：用 `system_clock` 测时长；跨来源直接比较时间戳；窗口无界；同时间戳当重复；flush 未定义；倒退后水位回退。
- 与 ROS2 的关联：消息头时间戳是 event time，回调执行是 processing time，不能混用；迁移实验注入延迟并记录实际顺序与丢弃计数。

## 58 QoS 概念映射

- 目标：对照 reliability/durability/history/depth 设计实验，分清 DDS/ROS2 保证与应用层约定。
- 核心概念：reliable/best_effort 影响重传与丢失；volatile/transient_local 决定晚加入者能否看历史；keep_last(depth)/keep_all 决定保留量；QoS 需发布订阅兼容；中间件不保证应用处理/去重，也不替代背压。
- 参考实现思路：本机用应用层模型把四维差异变成计数器：深度队列；reliable 满时失败由调用方重试；best_effort 满时丢最旧；transient_local 保留最近 depth；volatile 晚加入读空。再用固定序列与慢消费者输出表格，并列 ROS2 对照实验。
- 关键代码片段 / 实验步骤：

```cpp
struct Profile { bool reliable; bool transient_local; std::size_t depth; };
class ModelTopic {
  std::deque<int> sub_q_, history_; bool tl_; std::size_t depth_;
public:
  ModelTopic(bool tl, std::size_t depth) : tl_(tl), depth_(depth) {}
  bool publish(int v, bool reliable) {
    if (sub_q_.size() == depth_) {
      if (reliable) { ++retried_; return false; } // 模型：调用方稍后重发
      ++dropped_; sub_q_.pop_front();             // best_effort 丢最旧
    }
    sub_q_.push_back(v);
    if (tl_) { if (history_.size() == depth_) history_.pop_front(); history_.push_back(v); }
    return true;
  }
  std::vector<int> late_join() const {
    return tl_ ? std::vector<int>(history_.begin(), history_.end())
               : std::vector<int>{};            // VOLATILE 不保留
  }
  std::size_t dropped_ = 0, retried_ = 0;
};
```

```bash

timeout 10 ./stage1/labs/58/run     # 打印四组配置的 dropped/retried/late_join
```

- 验收证据：depth=3 发 1..10 后晚加入，transient_local 得 `{8,9,10}`，volatile 为空；慢消费时 best_effort 有丢弃且收数变少，reliable 重试>0 且最终收齐。反例一 depth=1，晚加入得 `{10}`；反例二 reliable 但应用不消费，重试/内存增长；反例三不兼容 QoS 在真实 ROS2 不连接，本机待验证。逐项标注保证与约定。
- 常见坑：RELIABLE 当恰好一次；忽略 QoS 不兼容；`keep_all` 无界；depth 当应用队列。
- 与 ROS2 的关联：在装有 ROS2 的环境固定频率、订阅端慢处理，记录收发计数，验证 durability 与兼容性；记录发行版与输出，注明本机未安装。

## 59 Executor 回调组实验

- 目标：记录 SingleThreaded/MultiThreaded 与 MutuallyExclusive/Reentrant 行为，计时可重复，说明吞吐与死锁。
- 核心概念：executor 决定回调线程数，group 决定组内并发；互斥组同时最多一个回调，reentrant 可多个；单线程一律串行；互斥组内同步等同组回调死锁；reentrant 不等于线程安全。
- 参考实现思路：用计数信号量表示组容量（互斥 1、reentrant N），1/2 线程表示 executor；4 个各睡 50ms 任务测总耗时；死锁用例容量 1、A 等同组 B 的 future，仅一线程；记录线程 ID/起止，重复 3 次。
- 关键代码片段 / 实验步骤：

```cpp
struct Group {                              // MutEx: cap=1；Reentrant: cap=N
  explicit Group(std::ptrdiff_t cap) : sem(cap) {}
  std::counting_semaphore<> sem;
};
void work(Group& g) {
  g.sem.acquire();                          // 组内并发许可
  auto t0 = std::chrono::steady_clock::now();
  std::this_thread::sleep_for(std::chrono::milliseconds(50));
  auto t1 = std::chrono::steady_clock::now();  // 记录线程 ID 与区间
  g.sem.release();
}
// 4 个任务：Single=顺序；Multi+MutEx=同组串行；Multi+Reentrant=并行
```

```bash
timeout 5 ./stage1/labs/59/run single
timeout 5 ./stage1/labs/59/run multi_mutex
timeout 5 ./stage1/labs/59/run multi_reentrant 2
timeout 5 ./stage1/labs/59/run deadlock        # 预期 exit 124
```

- 验收证据：2 线程、4×50ms 预期 200/200/100ms，记录 3 次实测取 p50；死锁用例 `timeout 5` 退出 124。反例一单线程配 reentrant 仍 200ms，组不造线程；反例二 reentrant 共享计数不加锁，TSan 报竞争/丢数；反例三互斥组内 `sleep` 只降吞吐，用时间线区分慢与死锁。
- 常见坑：以为多线程会自动并发同一回调；以为 group 限制 QoS 或顺序；跨组加锁死锁；回调内同步调用。
- 与 ROS2 的关联：在装有 ROS2 的环境把两个订阅分放互斥/可重入组，用单/多线程 executor 运行；回调打印线程 ID、起止并睡眠；记录发行版、线程数与吞吐。

## 60 CLI 日志与指标

- 目标：日志级别、计数器、延迟直方图最小模块；异常可定位，p50/p99 合理。
- 核心概念：级别过滤在格式化前；日志带时间/级别/上下文；计数器原子或加锁；直方图用固定桶，百分位按 nearest-rank 并写明；平均值不能替代 p99；异常记操作名、输入与 `what()` 并计数。
- 参考实现思路：Logger 持阈值；Metrics 用原子计数和 12 个延迟桶，`upper_bound` 定位并钳制溢出；百分位按 `ceil(p*n)` 排名取桶上界；主程序解析 `--log-level` 与 `--fail-every`，正常/异常同路径并打印 `total/ok/error/p50/p99`。
- 关键代码片段 / 实验步骤：

```cpp
enum class Level { Error = 0, Warn, Info, Debug };
class Metrics {
  static constexpr std::array<std::uint64_t, 12> kBounds{
    1,2,5,10,20,50,100,200,500,1000,2000,5000};
  std::array<std::uint64_t, 12> buckets_{};
  std::atomic<std::uint64_t> total_{0}, errors_{0};
public:
  void observe_us(std::uint64_t us) {
    ++total_;
    auto it = std::upper_bound(kBounds.begin(), kBounds.end(), us);
    auto idx = std::size_t(it - kBounds.begin());
    ++buckets_[std::min<std::size_t>(idx, kBounds.size() - 1)];
  }
  std::uint64_t pct(double p) const {
    auto n = total_.load(); if (!n) return 0;
    auto rank = std::uint64_t(std::ceil(p * double(n)));
    std::uint64_t seen = 0;
    for (std::size_t i = 0; i < buckets_.size(); ++i)
      if ((seen += buckets_[i]) >= rank) return kBounds[i];
    return kBounds.back();
  }
};
```
